# Project Specification

Status: Draft for owner review · Last updated: 2026-10-01

## 1. Purpose

CAIPO supports the research project *"AI Policy and Economic Transformation in Central Asia: A Comparative Analysis of Turkmenistan and Uzbekistan"*. It is both the working environment in which the research is done and the record that makes the research checkable by others.

It holds four kinds of material and keeps them connected:

1. **Documents**: AI policy, legal, and regulatory texts and related reports, stored as obtained with full provenance.
2. **Structured policy records**: policies, their stated objectives, instruments, sectors, responsible institutions, and formal lifecycle events, coded by researchers from the documents.
3. **Indicators**: economic and socioeconomic time series from identified providers, stored by release so revisions are visible.
4. **Claims and evidence**: research statements, each typed by what kind of statement it is and linked to the passages, observations, analyses, or recorded searches that support it.

On top of these it provides comparative views and an AI assistant that answers questions only from retrieved evidence.

## 2. Scope

### In scope

- Turkmenistan and Uzbekistan as the initial countries
- Documents in Turkmen, Uzbek (Latin and Cyrillic), Russian, and English
- Ingestion of documents and datasets submitted by authorised Researchers
- Structured coding of policies
- Import of indicator data from external providers
- Typed claims with evidence and review, including negative findings backed by recorded searches
- Side-by-side comparison of policies and indicators
- Keyword search over approved documents
- Evidence-grounded question answering with verified references
- Export of data with provenance for use in publications
- Evaluation of the AI pipeline

### Out of scope

- Automated web crawling or monitoring without a Researcher in the loop
- Economic forecasting
- Causal estimation of policy effects (see [LIMITATIONS.md](LIMITATIONS.md))
- Policy recommendations generated by AI
- AI-suggested policy coding and AI-drafted research claims, until a separate safe design exists and is ratified
- Machine translation presented as authoritative text
- A public write API
- Real-time collaboration features

## 3. Users and roles

The access model is not yet decided (blocker B5). The roles below are the working assumption. These four are the only roles; documents must not use other role names.

| Role | Can |
|---|---|
| Reader | Browse approved content, view comparisons, ask the assistant |
| Researcher | Reader, plus register sources, submit documents and datasets, code policies, record searches, draft claims |
| Reviewer | Researcher, plus approve documents, set rights, change a source's allowed hosts, approve claims |
| Administrator | Manage users, configuration, and operational tasks; perform redaction |

Whether Reader is anonymous public access or an authenticated account is the open question. ADR-0007 proposes that the assistant requires an authenticated account at least initially.

## 4. Functional requirements

Requirement IDs are stable and referenced by tests and PRs.

### Sources and documents

- **FR-01** Register a source with its type, publisher, source tier, and allowed hosts.
- **FR-02** Acquire a document by URL or upload, storing the exact bytes, a content hash, and the acquisition record. Distinguish an origin the system observed from one the uploader attests.
- **FR-03** Keep every version of a document. A re-fetch with different content creates a new version.
- **FR-04** Extract text into addressable segments with locators (page, article, paragraph).
- **FR-05** Record language, script, and whether a version is an original, an official translation, or an unofficial translation.
- **FR-06** Require Reviewer approval before a document becomes citable or searchable.
- **FR-07** Track every ingestion request through defined states, including failures that produce no document.
- **FR-08** Record the rights that apply to each document version and enforce them on display, export, and transmission to external services.

### Policies

- **FR-10** Record policies with country, issuing institution, and formal lifecycle events (adopted, amended, entered into force, expired, repealed). Derive policy status from those events.
- **FR-11** Record stated objectives, instruments, and sectors, each linked to the passage it was coded from.
- **FR-12** Record relationships between policies (amends, supersedes, implements).
- **FR-13** Record implementation information only as claims of type implementation evidence, never as policy events.

### Indicators

- **FR-20** Define indicators with unit, definition, and provider.
- **FR-21** Import observations as a dated release from a provider and keep earlier releases.
- **FR-22** Represent missing, estimated, and provisional values explicitly.

### Claims and evidence

- **FR-30** Record a claim with exactly one epistemic type, a confidence level with rationale, and an origin.
- **FR-31** Link claims to supporting and contradicting evidence: passages, observations, analysis runs, or search runs.
- **FR-32** Enforce evidence requirements per claim type before a claim can be approved.
- **FR-33** Record who drafted, reviewed, and approved a claim, and keep its history.
- **FR-34** Record a search for sources as a SearchRun, and allow a negative-finding claim to be evidenced by it.
- **FR-35** When evidence behind an approved claim becomes unavailable, mark the claim as needing reassessment and stop presenting it as approved, without deleting anything.

### Comparison and search

- **FR-40** Compare policies across countries by sector, instrument type, institution, and time.
- **FR-41** Compare indicator series across countries with visible missing data and provider notes.
- **FR-42** Present formal policy events and indicator series on a shared time axis without implying causation. Testable criteria: (a) no connecting annotations, fitted lines across events, or computed "effect" values; (b) the standard non-causation notice is shown; (c) missing-data and estimate flags are shown; (d) all interface text for the view passes the prohibited-wording check.
- **FR-43** Search approved documents by keyword with filters, without AI. Delivered with the retrieval app in Phase 5. Before then, documents are found by browsing and filtering metadata.

### AI assistant

- **FR-50** Answer questions using only retrieved, approved evidence whose rights permit it.
- **FR-51** Attach to every statement its references, a permitted assistant label, server-rendered attribution to its source, and uncertainty flags.
- **FR-52** Abstain when evidence is insufficient and say what is missing.
- **FR-53** Record each interaction with enough detail to audit it.
- **FR-54** Mark all assistant output as AI-generated synthesis, and mark statements written in a different language from their source as AI translation or paraphrase.
- **FR-55** Display only verified output.

### Export

- **FR-60** Export claims with their evidence (passages, observations, analysis runs, search runs) and indicator data with provenance in open formats, respecting rights and neutralising spreadsheet formulas.
- **FR-61** Produce a corpus manifest listing every document version and its hash.

## 5. Non-functional requirements

Priority order when they conflict: correctness, security, maintainability, testability, reproducibility, observability, performance, clarity of presentation.

| ID | Requirement |
|---|---|
| NFR-01 | No claim can be approved without the evidence its type requires. Enforced in the service layer and tested. |
| NFR-02 | The system cannot display a source reference that does not resolve to a stored Passage or Observation. |
| NFR-03 | Provenance records are append-only, except through the recorded redaction procedure for legally or privacy-required removal ([DATA_MODEL.md](DATA_MODEL.md) §7). |
| NFR-04 | All external content, documents and datasets alike, is processed under the controls in [SECURITY.md](../SECURITY.md). |
| NFR-05 | A fresh environment can be built from the repository and a data snapshot with documented commands. |
| NFR-06 | Every request and background task carries a correlation ID through logs. |
| NFR-07 | The platform runs on a single modest server. Expected scale is thousands of documents and a small number of concurrent users. Performance targets are set after the first measurements, not guessed. |
| NFR-08 | Adding a country requires data entry only: no new tables, columns, apps, or conditional code. Adding a **language** may additionally require language-specific database configuration (for example a text search configuration, applied by a migration) and a retrieval evaluation for that language. |
| NFR-09 | The interface supports Unicode text in all project languages and scripts. |
| NFR-10 | Persistent accounting, including AI budgets, lives in PostgreSQL. Nothing that must survive a restart is held only in Redis. |

## 6. Extensibility: adding a country

Adding Kazakhstan, Kyrgyzstan, or Tajikistan must require:

1. A `Country` record
2. Its institutions and sources
3. If it introduces a new language: a Language record, any language-specific database configuration, and a retrieval evaluation for that language

It must not require new tables or columns, new apps, or conditional code. This is tested by using a synthetic third country in the test suite from the start.

| 0 | Architecture and research foundation | Architecture gate READY for Phase 1 |
| 1 | Project skeleton, tooling, CI, containers, authentication, countries and institutions | A deployable empty system with all quality checks enforced |

| 3 | Policy coding and indicator import | Structured records linked to passages and releases |

Each phase has its own gate check: its blockers in §10 must be closed before it starts.

Consequences:

- Docker must be enabled before Phase 1 (blocker B1).
- **Feasibility of running embedding or generation models locally has not been assessed.** A GPU with 12227 MiB is present and the WSL memory allocation is adjustable, so no hardware limitation is asserted. The production server is not yet specified. This is part of blocker B14.
- Whether GPU access works from inside Docker containers on this machine is unknown until Docker is enabled.
- Python development tools will be installed per project through `uv`, so their absence system-wide is not a problem.
- Compatibility of the chosen Django release and of every parser and database library with the chosen Python version must be confirmed when dependencies are first locked (blocker B4). The same applies to every version-specific statement in these documents.
- Mermaid diagrams in these documents could not be rendered locally (no Node toolchain). Their syntax was checked by script only.
